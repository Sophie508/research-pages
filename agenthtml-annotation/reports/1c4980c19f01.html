SAS parser trips on datastep & procedure options.

The Issue

Options break the grammar.

A SAS data step or proc may carry options delimited by a slash. The current parser has no production for that token, so it bails on a syntax error instead of recording the option list.

🪓

Unexpected token /

After the dataset name the parser expects a semicolon or statement body; the slash option separator isn't in any rule.

📐

Missing grammar rule

Both data and proc rules need an optional / option_list clause that captures key=value pairs.

🧪

No regression test

The suite never asserted this form, so the regression slipped in silently.

Outcome

Reproduced, not repaired.

The agent correctly isolated the failing input and reasoned about the grammar change, but the submitted diff doesn't touch the parser source — only the repro file.

⚠️

Partial credit: reproduction only

The real fix would extend the data/proc productions with an optional / option_list and add a regression test. This run stopped at capturing the failing snippet — a useful artifact, but not the patch the issue asked for.

FAQ

Frequently asked.

Why did the parser fail on the slash? ＋
SAS allows data name / option=value …; and proc name / options;. The parser's productions jumped from the dataset/proc name straight to the statement body or semicolon, so the / was an unexpected token.
What would a correct fix look like? ＋
Add an optional SLASH option_list branch to both data and proc rules, where option_list parses key or key=value pairs separated by whitespace, then store them on the AST node for later rendering.
Why couldn't the agent run the probe parser? ＋
The throwaway script imported ply, which wasn't installed in the sandbox, and the environment blocks interactive installs. The sas runtime was also absent, so neither direct execution nor a probe run was possible.
Is the reproduction file itself useful? ＋
Yes — it pins the exact failing input (data test / view=testvew;) so a future fix can drop it straight into the test suite as a regression case.
