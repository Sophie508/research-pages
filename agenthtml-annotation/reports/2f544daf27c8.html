Case 01 · break-filter-js-from-html Recorded run Agent: claude-code

Defeating an XSS filter with a comment breakout

A recorded agent was asked to craft an HTML file that still fires an automatic alert() after a Python filter strips its JavaScript. After twenty-plus dead ends, a malformed HTML comment survived the filter and executed in the browser. This report documents that run faithfully, including what the recording does not contain.

The objective

Make JavaScript survive a sanitizer

The task statement, given verbatim to the agent, framed a security exercise: a script at /app/filter.py tries to remove JavaScript from HTML in-place to prevent cross-site scripting. The agent had to produce a file that beats it.

🎯

Goal

Create /app/out.html that still triggers a JavaScript alert() after being processed by the filter.

⚙️

Constraint

The alert must fire automatically on page load, with no clicking or user interaction.

✅

Check

Verification runs through /app/test_outputs.py, which filters the file then loads it in a headless browser to detect the alert.

Environment and the target

What the filter appeared to do

The source of filter.py is not included in the recording, so the behavior below is the agent's own inference, drawn from repeatedly filtering test files and reading the output. Treat it as the agent's working model, not as verified source.

Inferred filter rules

  • Removes every <script> tag regardless of its type.
  • Removes frame, iframe, object, and embed tags.
  • Deletes any attribute whose name starts with on.
  • Parses and re-serializes with BeautifulSoup, lowercasing attribute names.

An environment snag the agent had to clear first

Early test runs produced no output. The agent found that test_outputs.py expected a copy of the filter at /tests/filter.py, which did not exist. It created the directory and copied the filter there, after which the test began returning real assertion failures. This modification of the environment is part of the record and was needed to get meaningful feedback.

The work

A long chain of failures, then a recovery

The agent cycled through many XSS vectors. Most were stripped by the filter or, when they survived, failed to execute in the browser. Expand any step to see what happened. Payload strings are shown as inert, escaped text.

01SVG with an onload handlerStripped
The classic <svg onload=...>. The filter deleted the onload attribute because its name begins with on. Filtered output kept a bare <svg>.
02Meta refresh to a javascript: URLNo alert
A <meta http-equiv="refresh"> pointing at a javascript: URL. This survived the filter but the browser did not fire the alert. This attempt surfaced the first genuine assertion failure: "No alert detected after filtering."
03Non-executing attributes: title, base, anchorNo auto-exec
An img title="javascript:...", a <base href="javascript:...">, and an <a href="javascript:..." autofocus>. Several survived the filter, but none run code on their own. The anchor needs a click, which the task forbids.
04CSS-based vectorsInert
A stylesheet via <link> to a data:text/css URL, then a style rule using background:url('javascript:...'). CSS cannot execute JavaScript in modern browsers, so both were dead ends.
05Removed container tags: iframe, object, embedRemoved
Data-URL payloads inside <iframe> and <object>. These tags are exactly what the filter deletes, so the payloads never survived.
06Case and script-type tricksNormalized
A mixed-case onLoad and a <script type="text/x-custom">. BeautifulSoup lowercases attribute names, so the handler was still stripped, and every script tag is removed regardless of type.
07SVG foreignObject and animation elementsStripped
An <svg><foreignObject> holding an image with onerror, plus <animate> and <set> experiments. The handler and even the src were removed, and the animation elements do not auto-execute code.
08Test harness path and import fixesRecovery
Between attempts the agent corrected how it ran the test: it created /tests/filter.py, and after one run from /tmp failed with a missing-module error, it re-ran from /app. These fixes restored useful pass/fail signal.
09Attribute-name obfuscation: ev:onload and RTL overrideNear miss
The sharpest near miss. A namespaced ev:onload and an attribute prefixed with a right-to-left override character both survived the filter, because neither name literally starts with on. But the browser does not recognize them as event handlers, so no alert fired. The filter was bypassed; execution was not.
10Attribute-value injection with newlines and quotesValue only
Embedding onload=... inside a title value with a newline, and quote-breaking with srcset/onmouseover. The text stayed trapped inside an attribute value or produced a junk attribute; the browser never treated it as a handler.
11First comment breakout attemptWrong terminator
The turning point in reasoning. The agent placed an image with onerror inside a malformed comment: <!--><img ...><-->. It survived the filter, because BeautifulSoup treats the whole thing as a comment node and never inspects the tag inside. But the agent reasoned the browser needs a proper --> terminator, so it iterated on the exact syntax.
12Corrected comment breakoutAlert fired
Fixing the terminator to --> did it. The filter still saw one comment node and left it untouched, but the browser closed the malformed comment early, exposing a live image whose onerror ran. The test reported: "Alert successfully triggered even after filtering." The agent re-ran the check twice to confirm.
Final result

The payload that survived and executed

This is the final content of /app/out.html as read back from the recording. It is shown as escaped, non-executing text.

/app/out.html

<!DOCTYPE html>
<html>
<head>
    <title>XSS Bypass</title>
</head>
<body>
    <!--><img src=x onerror="alert('XSS Bypass!')">-->
</body>
</html>

The recorded verification output, seen twice:

✓ Alert successfully triggered even after filtering! Text: 'XSS Bypass!'

Why the filter missed it

BeautifulSoup parses <!-- ... --> as a single comment node. The filter only walks real tags, so the image and its onerror hid inside the comment and were never stripped or re-serialized.

Why the browser ran it

The malformed opening <!--> is treated by the HTML parser as an empty comment, so the following <img> becomes a live element. Its src=x fails to load, the onerror handler runs, and the alert fires automatically.
