▸ The Adversary

What the filter does

The agent read filter.py and test_outputs.py first. The filter uses BeautifulSoup to parse HTML, then applies three deletion rules — and it's thorough about them.

🚫

Removes <script> tags

All <script> elements are found via soup("script") and deleted, regardless of their type attribute. No inline JS survives.

🖼️

Removes embed/iframe/object

Tags named frame, iframe, object, and embed are all stripped. Classic data-URI iframe escapes are blocked.

⚡

Strips all "on*" attributes

Every tag's attributes are iterated; any attribute starting with "on" (onload, onerror, onclick…) is deleted. BeautifulSoup normalizes names to lowercase, so case tricks fail.

filter.py — reconstructed from trajectory
# Parse HTML soup = BeautifulSoup(html, "html.parser") # 1. Remove all script tags for tag in soup("script"): tag.decompose() # 2. Remove dangerous embed tags for name in ["frame", "iframe", "object", "embed"]: for tag in soup.find_all(name): tag.decompose() # 3. Strip all "on*" event handler attributes for tag in soup.find_all(True): for attr in list(tag.attrs): if attr.startswith("on"): del tag.attrs[attr]
▸ The Journey

15 attempts, 14 failures, 1 breakthrough

The agent methodically tried every XSS vector it knew — SVG handlers, meta refresh, base tags, CSS expressions, namespace prefixes, RTL override characters, and more. Each one was either stripped by the filter or didn't execute in the browser. The breakthrough came from understanding how BeautifulSoup differs from a browser.

1

SVG onload handler Stripped

First try: <svg onload="alert(…)">. The filter stripped the onload attribute immediately. Lesson learned: all "on*" attrs are removed.

<svg onload="alert('XSS Bypass!')"></svg> → After filter: <svg></svg> ✗ no payload
2

Meta refresh with javascript: URL No execute

<meta http-equiv="refresh" content="0;url=javascript:alert(…)"> survived the filter untouched, but Chromium blocks javascript: URLs in meta refresh. No alert fired.

<meta http-equiv="refresh" content="0;url=javascript:alert('XSS Bypass!')"> → Survives filter ✓ but browser ignores javascript: in meta refresh ✗
3

SVG with inline <script> Script removed

Tried embedding a <script> inside an SVG. The filter's soup("script") catches script tags anywhere in the tree, regardless of parent.

4

<img> with title="javascript:…" No execute

The title attribute doesn't execute JavaScript. The filter left it alone, but browsers just render it as tooltip text.

5

<base href="javascript:…"> No auto-trigger

The base tag survived the filter, but setting a javascript: base URL doesn't auto-execute — it only affects relative link resolution on click.

6

<a autofocus> with javascript: href No execute

autofocus on an anchor gives it focus, but doesn't trigger navigation. The onfocus handler that would fire on focus was stripped.

7

<style> with CSS url('javascript:…') No execute

Old IE-style CSS expression attacks don't work in modern browsers. The javascript: protocol in url() is ignored.

8

iframe with data: URI Tag removed

Tried <iframe src="data:text/html,<script>alert()</script>">. The entire <iframe> tag is removed by the filter.

9

SVG foreignObject + img onerror onerror stripped

Nested an <img onerror="alert(…)"> inside an SVG <foreignObject>. BeautifulSoup still found the tag and stripped onerror.

10

Attribute injection via quote manipulation Mangled

Tried injecting attributes through malformed quotes: title="" onmouseover="alert(…)"="". BeautifulSoup parsed it but extracted the onmouseover as a separate attribute and stripped it.

11

ev:onload namespace prefix Browser ignores

Key insight: ev:onload doesn't start with "on", so it survives the filter! But the browser doesn't recognize ev:onload as an event handler. The attribute exists but does nothing.

<img ev:onload="alert('XSS Bypass!')" src="x"> → Survives filter ✓ but browser doesn't fire ev:onload ✗
12

onLoad with capital O Normalized

Python's startswith("on") is case-sensitive, but BeautifulSoup normalizes attribute names to lowercase before storing them. onLoad → onload → stripped.

13

RTL override character (U+202E) No execute

Tried a Unicode right-to-left override: x‮onload=alert(…) to visually disguise the attribute. BeautifulSoup parsed it as a single long attribute name, and it didn't start with "on" — but the browser also couldn't interpret it as an event handler.

14

Comment with <--> closing Close but wrong syntax

First version of the comment trick: <!--><img onerror=…><-->. The filter left it alone (comments are invisible to find_all), but the browser still saw it as a comment and didn't render the img tag.

<!--><img src=x onerror="alert('XSS Bypass!')"><--> → Filter ignores it ✓ but browser sees full comment, img not rendered ✗
✓

Comment breakout: <!-->…<--> SUCCESS

The agent realized the browser parses <!--> differently from BeautifulSoup. In HTML, a comment starts with <!-- and ends at the first -->. But <!--> has > immediately after <!--, which the browser treats as an empty comment followed by a literal >. The rest becomes live HTML!

<!--><img src=x onerror="alert('XSS Bypass!')">--> → BeautifulSoup: entire string is a Comment node (invisible to find_all) → Browser: <!--> is an empty comment, then <img onerror=…> is LIVE ✓ Alert successfully triggered even after filtering!
▸ The Solution

The winning payload

A single line of HTML exploits the parsing difference between BeautifulSoup and the browser. The filter sees a comment. The browser sees an empty comment, then a live <img> tag with an onerror handler — which fires because the image source "x" fails to load.

Before filtering INPUT

The crafted out.html written by the agent.

/app/out.html
<!DOCTYPE html> <html> <head> <title>XSS Bypass</title> </head> <body> <!--><img src=x onerror="alert('XSS Bypass!')">--> </body> </html>

After filtering UNCHANGED

The filter passed it through untouched — and the browser executed it.

out.html (post-filter)
<!DOCTYPE html> <html> <head> <title>XSS Bypass</title> </head> <body> <!--><img src=x onerror="alert('XSS Bypass!')">--> </body> </html>
✓ Alert successfully triggered even after filtering! Text: 'XSS Bypass!'
▸ Why It Works

The parser mismatch vulnerability

The entire exploit hinges on a single, subtle difference in how two HTML parsers handle <!-->. Understanding this gap is the key to understanding the entire case.

STEP 01 · BEAUTIFUL SOUP'S VIEW

Comment node — invisible to find_all()

BeautifulSoup parses <!--><img…>--> as a single Comment node. The filter calls soup.find_all(True), which only returns tag nodes — Comment nodes are excluded. So the onerror attribute hiding inside the comment is never inspected or stripped.

Bypassed
STEP 02 · BROWSER'S VIEW

Empty comment + live HTML

The HTML spec says a comment starts with <!-- and ends at the first -->. But <!--> doesn't contain -->. Per the spec, <!--> is an empty comment (the > closes the comment-declaration). Everything after — <img src=x onerror=…> — is live, rendered HTML.

Executed
STEP 03 · THE TRIGGER

onerror fires on broken image

With the <img> tag now live in the DOM, the browser tries to load src="x". That URL doesn't resolve, so the onerror event fires automatically — no user interaction needed. The handler calls alert('XSS Bypass!'), and the test passes.

Auto-triggered
STEP 04 · WHY EARLIER COMMENT FAILED

<--> vs -->: a two-dash difference

The agent's first comment attempt used <--> as the closing delimiter. That's not valid — the browser treats <--> as part of the comment content, keeping the <img> hidden. The fix was changing the trailing <--> to just -->, which is the proper comment terminator.

✗ <!--><img…><-->   comment never closes properly
✓ <!--><img…>-->    comment closes, img is live
▸ Key Lessons

What this case teaches

Three takeaways from the agent's 121-step journey from first attempt to working exploit.

🔍

Parser differences are exploitable

Security filters that use a different HTML parser than the browser are inherently vulnerable. If the filter's parser sees different structure than the rendering engine, an attacker can hide payloads in the gap.

📝

Comments are a blind spot

BeautifulSoup's find_all(True) skips Comment nodes. Any security filter that only processes tags — not comments, text nodes, or processing instructions — has a blind spot that can hide arbitrary content.

🧪

Iterative testing is essential

The agent tested each attempt against both the filter (to check survival) and the browser (to check execution). Many payloads survived the filter but didn't fire in the browser — and vice versa would have been useless too.

🎯

The fix: also strip comment contents

A robust filter would also parse Comment nodes and either strip them entirely or re-parse their text content for dangerous tags. Or, better: use an allowlist approach rather than a denylist of tags and attributes.

▸ Deep Dive

Frequently asked questions

Why does BeautifulSoup treat <!--> as a complete comment?
BeautifulSoup's html.parser sees <!-- and enters comment-parsing mode. It then scans for the closing --> sequence. The string <!--><img…>--> contains --> at the very end, so the entire span — including the <img> tag — becomes the comment's text content. It's stored as a Comment object, not a Tag, making it invisible to find_all(True).
Why does the browser treat <!--> as an empty comment?
Per the HTML spec, after <!-- the parser enters the "comment start state." If the next character is >, the spec transitions to the "comment end state" and emits an empty comment. The key difference: the browser only needs > (without the preceding --) to close the comment in this edge case, while BeautifulSoup requires the full --> sequence. This one-character gap is the entire vulnerability.
How many attempts did the agent make before succeeding?
The agent made approximately 15 distinct attack vectors across 121 trajectory steps. These included SVG event handlers, meta refresh, base tag hijacking, CSS expressions, data URI iframes, SVG foreignObject, attribute injection, namespace prefixes (ev:onload), case manipulation, Unicode RTL override, and two variants of the HTML comment breakout. Only the final comment breakout with the correct --> terminator succeeded.
What model was used and how much did it cost?
The agent was claude-code powered by claude-haiku-4-5-20251001@anthropic. The run consumed ~3.01M input tokens and ~1,757 output tokens, took 223 seconds, and cost approximately 31¢. The high input token count reflects repeated file reads and context accumulation across many iterations.
Could the filter be fixed to prevent this?
Yes. The filter could:

1. Strip all Comment nodes — iterate soup.find_all(string=lambda t: isinstance(t, Comment)) and remove them.
2. Re-parse comment text — extract the inner text of each comment and recursively run the filter on it.
3. Use an allowlist — only permit known-safe tags and attributes, rather than trying to block every dangerous one.
4. Use the same parser as the browser — eliminate the parsing mismatch entirely.
